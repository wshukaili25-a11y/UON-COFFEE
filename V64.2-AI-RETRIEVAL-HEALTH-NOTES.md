# UON Hub V64.2 — Precise AI Retrieval + Connector Health

V64.2 improves UON AI retrieval precision without changing the public/private data boundary introduced in V64/V64.1.

## 1. Trusted University knowledge chunking

Long `university_page` rows in `uon_ai_knowledge` are now retained as provenance parents and split into smaller derived retrieval rows.

Rules:

- split only official `university_page` rows longer than 1600 characters,
- chunk window: 1500 characters,
- step: 1300 characters,
- overlap: about 200 characters,
- maximum: 20 chunks per parent,
- derived rows use `metadata.derived_chunk = true`,
- derived rows retain the parent source URL/title, confidence and verification state,
- parent rows remain stored but become `active=false` after chunking,
- approved derived chunks remain `active=true` and are therefore used by the existing search path.

Current live result after backfill/hotfix:

- 22 derived University chunks,
- 22 active chunks,
- 6 hidden provenance parents,
- chunk sizes: 380–1500 characters,
- no tiny trailing chunks under 300 characters.

## 2. Trigger safety

The chunk refresh trigger runs when:

- an official University parent is inserted,
- its `content_hash` changes,
- or a hidden parent is explicitly reactivated by an upstream update.

It does not recursively regenerate children when it hides the parent.

A rollback simulation of a future source update preserved:

- 22 active derived chunks,
- 6 hidden parents.

The chunk refresh/trigger helpers are `SECURITY DEFINER`, but EXECUTE is revoked from `PUBLIC`, `anon` and `authenticated`; only `service_role` can execute the refresh helper directly.

## 3. Better intent routing in `uon-ai-chat-v64`

V64.2 distinguishes physical place questions from informational questions before Maps routing.

Examples:

- `وين أقرب مطبعة من جامعة نزوى؟` → physical place / Maps flow.
- `وين ألقى التقويم الأكاديمي لجامعة نزوى؟` → informational calendar flow, no Maps fallback.
- plural `برامج` queries are canonicalized so the existing V3 assistant resolves them as `programs` rather than `general`.

The original user question is preserved for the conversation. A `resolved_question` field may be included for debugging/verification when the gateway canonicalizes a question before passing it to the existing V3 assistant.

Live post-deploy checks:

- Programs query → HTTP 200, `mode=programs`, official source, `live_official_sources=1`.
- Academic calendar query beginning with `وين ألقى` → HTTP 200, `mode=calendar`, official calendar source, no Google Maps connector.

`uon-ai-chat-v64` is ACTIVE as version 4.

## 4. Source Hub health view

`admin-ai-sources.html` now includes a health section. It exposes only booleans/counts, never secret values.

Health indicators:

- Google Auth provider enabled,
- Google Maps live configuration present,
- personal Google OAuth refresh configuration present,
- Google Drive Service Account configuration present,
- active University knowledge chunks and hidden parents.

`uon-ai-source-admin-v64` version 2 is ACTIVE and retains the existing `x-admin-password` authorization check. A live unauthenticated request returned HTTP 401.

## 5. Google/privacy boundary remains unchanged

V64.2 does not broaden Google scopes or public data access:

- Calendar remains `calendar.events.readonly`,
- Drive remains `drive.file`,
- personal Calendar/Drive data does not enter `uon_ai_knowledge`,
- Places details remain transient; durable Maps storage is limited to allowed place identifiers/UON-owned metadata,
- Google account connection remains optional.

## 6. Database security check

Supabase Security Advisor was rerun after the V64.2 migrations.

- No new advisor warning targets `uon_ai_refresh_knowledge_chunks_v642` or the V64.2 chunk trigger.
- The project still has pre-existing legacy advisor notices (RLS-without-policy informational notices and older public SECURITY DEFINER functions). Those are separate hardening work and should not be changed blindly because some are intentionally public application APIs.
