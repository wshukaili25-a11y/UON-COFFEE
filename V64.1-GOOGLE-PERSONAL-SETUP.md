# UON Hub V64.1 — Personal Google Connection

> This document describes the personal Google connection architecture introduced in V64.1. The current branch release is V64.2; retrieval/chunking and connector-health changes are documented in `V64.2-AI-RETRIEVAL-HEALTH-NOTES.md`. The personal Google privacy/scopes architecture below remains unchanged.

V64.1 adds an **optional** personal Google connection for students. Local UON Hub schedule/tasks/Focus data still works without an account. Personal Google Calendar/Drive data never feeds the public `uon_ai_knowledge` table.

## What V64.1 requests

Google OAuth additional scopes:

- `https://www.googleapis.com/auth/calendar.events.readonly`
  - Read events only.
  - V64.1 does not create, edit, or delete Calendar events.
- `https://www.googleapis.com/auth/drive.file`
  - Access only to specific Drive files used/authorized with the app.
  - V64.1 intentionally does not request `drive.readonly` or full `drive` access.

Supabase/Google also use the standard identity scopes required for Google sign-in (`openid`, email, profile).

## Google Cloud setup

1. Use the Google Cloud project for UON Hub or create a dedicated production project.
2. Enable:
   - Google Calendar API
   - Google Drive API
3. Open **Google Auth Platform** and configure Branding/Audience/Data Access.
4. Add the two V64.1 scopes above to Data Access.
5. Create a **Web application** OAuth client.
6. Authorized JavaScript origins:
   - `https://uonhub.space`
   - `https://www.uonhub.space`
   - add localhost only for local development, then remove it from production if it is not needed.
7. Authorized redirect URI for Google must be the Supabase Auth callback:
   - `https://irkhvydgxpseflggbeqq.supabase.co/auth/v1/callback`
8. Save the Client ID and Client Secret.

Because Calendar user-data scopes may be treated as sensitive, an external public OAuth app may require Google verification before broad production use.

## Supabase Auth setup

In Supabase Dashboard → Authentication → Providers → Google:

- enable Google,
- set the same Web Client ID,
- set the same Web Client Secret.

In Authentication URL configuration / Redirect URLs, allow:

- `https://uonhub.space/google-connect.html`
- `https://www.uonhub.space/google-connect.html`
- the Vercel preview pattern only if you intentionally want OAuth testing on previews.

The browser uses Supabase Auth PKCE with `detectSessionInUrl: true`.

## Edge Function secrets

`uon-google-account-v64` needs the same OAuth client credentials server-side so it can refresh Google access tokens without asking the student to reconnect every hour:

- `GOOGLE_OAUTH_CLIENT_ID`
- `GOOGLE_OAUTH_CLIENT_SECRET`

Do not place them in browser JavaScript, GitHub files, or SQL migrations.

Supabase already provides the server-side project URL/service-role environment variables to the Edge Function runtime.

## Token handling

1. Google redirects back through Supabase Auth.
2. The initial `provider_token` / `provider_refresh_token` are passed immediately from the authenticated browser session to `uon-google-account-v64`.
3. The Edge Function validates the Google access token and reads the actual granted scopes from Google token info.
4. Tokens are stored through service-role-only RPC functions into **Supabase Vault**.
5. `uon_google_connections` contains only metadata and Vault secret IDs.
6. The page calls `refreshSession()` after capture and never writes Google tokens to a custom localStorage key.
7. Disconnect revokes the Google token when possible and deletes Vault secrets.

## Database isolation / RLS

Tables:

- `uon_google_connections`
  - one row per authenticated user,
  - authenticated users can SELECT only their own row,
  - users cannot directly INSERT/UPDATE/DELETE connection rows.
- `uon_google_connection_audit`
  - user can read only their own audit records,
  - writes are service-role only.

Vault helper RPC functions are `SECURITY DEFINER` but explicitly revoked from `PUBLIC`, `anon`, and `authenticated`; only `service_role` gets EXECUTE.

## Personal connector API

Edge Function: `uon-google-account-v64` (JWT required)

Actions:

- `status`
- `connect`
- `calendar-upcoming`
- `drive-files`
- `disconnect`

Calendar returns at most 12 upcoming events from the primary calendar.

Drive uses `drive.file`; therefore its list contains only files the OAuth grant allows this app to access. This limited behavior is intentional.

## Public knowledge separation

Do **not** insert any output from `uon-google-account-v64` into:

- `uon_ai_knowledge`
- `import_sources`
- public search indexes
- public analytics payloads containing event/file content

If a future feature lets a student publish a Drive file to UON Hub, it must be an explicit separate user action with review/approval rather than automatic ingestion.

## Google Maps fallback

V64.1 also improves Maps independently of Google account login:

- If Places API is configured, UON AI shows live Google Places cards.
- If Places API or connector secrets are unavailable, location questions still receive Google Maps search and directions links generated with the public Maps URL scheme.

This fallback does not claim that Google Places data was fetched live.

## Activation checklist

1. GitHub verifier passes.
2. Validate migration in a rollback transaction.
3. Apply `20260902204500_v641_google_personal_connections.sql`.
4. Run Supabase security advisors and inspect any new warnings.
5. Configure Google OAuth Client ID/Secret in Supabase Auth.
6. Add the two Edge Function OAuth secrets.
7. Deploy `uon-google-account-v64` with JWT verification enabled.
8. Update/deploy `uon-ai-chat-v64` Maps fallback.
9. Test with a Google test user:
   - connect,
   - confirm actual scopes,
   - load upcoming Calendar events,
   - load Drive files authorized to the app,
   - refresh after access token expiry or force a refresh test,
   - disconnect and verify Vault secrets are removed.
10. Verify no personal event/file data appears in public knowledge queries.
11. Keep the PR in draft until the OAuth end-to-end test passes.
